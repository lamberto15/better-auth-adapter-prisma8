# How the adapter works

Background for contributors and the curious. You don't need any of this to
use the adapter; see the [README](../README.md) for that.

## Why this isn't a port of the Prisma 7 adapter

Prisma 8 ("Prisma Next") has a different query API from the classic
`PrismaClient` that Better Auth's own `prismaAdapter` targets, so this adapter
was written from scratch:

- **Models are namespaced.** It's `db.orm.public.User` on PostgreSQL, not
  `prisma.user`.
- **Filters are functions over fields**, not nested objects:
  `.where((u) => u.email.eq(x))` instead of `{ email: { equals: x } }`. The
  operators are `eq`, `neq`, `gt`, `lt`, `gte`, `lte`, `like`, `ilike`, `in`,
  `notIn`, `isNull` and `isNotNull`. `and` / `or` / `not` are standalone
  functions from `@prisma/orm-postgres/orm-client`.
- **Writes come in three forms**, and choosing the form is the API:

  | Form | Affects | Returns |
  | --- | --- | --- |
  | `create` / `update` / `delete` | one record | the record (`Row \| null` for update/delete) |
  | `createAll` / `updateAll` / `deleteAll` | every match | the records (`AsyncIterableResult<Row>`) |
  | `createAndCount` / `updateAndCount` / `deleteAndCount` | every match | the number affected |

  The installed package spells these `…AndCount`. Prisma's docs say
  `updateCount` / `deleteCount`, which don't exist in this version.

  `update()` and `delete()` change exactly one row even when the filter
  matches several, so `updateOne` / `deleteOne` map straight onto them.
- **Reads return an `AsyncIterableResult`.** It can be awaited to an array or
  streamed with `for await`, but only once. Pagination is `take(n)` / `skip(n)`.
- **Counting uses `aggregate`:** `aggregate((agg) => ({ total: agg.count() }))`.
- **There's no `$transaction`**, only `db.transaction(...)` with a callback.
- **There's no `{ increment: n }` shorthand**, so `incrementOne` and
  `consumeOne` read, recompute and write inside a transaction.

Useful import paths from `@prisma/orm-postgres`:

| What | Import path |
| --- | --- |
| client factory | `@prisma/orm-postgres/runtime` |
| `and` / `or` / `not` | `@prisma/orm-postgres/orm-client` |
| `AsyncIterableResult` | `@prisma/orm-postgres/components/runtime` |

## Transactions

`transaction` (default `false`) controls `adapter.transaction(cb)`, which
Better Auth and plugins use for multi-step writes.

- **`false`:** Better Auth's own default applies. The callback runs directly
  with no rollback, so a failure halfway through leaves the earlier writes in
  place.
- **`true`:** the callback runs inside a real `db.transaction(...)`, and an
  error rolls back every write made through it.

Separately, the single-row operations that must read and write together
(`consumeOne`, `incrementOne`, `update`, `delete`) always open their own
transaction when called on their own, whatever the setting. Inside an
existing transaction they reuse it.

Better Auth's transaction callback type doesn't expose `.transaction(...)`,
so plugins can't open nested transactions.

## Joins

With `advanced.database.joins: false` (the default), Better Auth resolves
joins itself with one extra query per joined model **for every row**.

With `joins: true`, this adapter fetches each joined model in **one** extra
query for all rows at once (`.where(f => f.to.in([...]))`) and groups the
results in memory. An N-row `findMany` goes from `1 + N` queries to
`1 + (number of joined models)`.

It isn't a single SQL `JOIN`: the adapter only sees the column pair Better
Auth resolved, not the contract's declared relations. A to-many join with a
per-row `limit` is trimmed in memory, so it may fetch more rows than a real
`JOIN` would. It still removes the per-row query cost, which is what the
option exists for. The conformance suite's `joins` tests and dedicated unit
tests check that each join is a single batched `.in(...)` query.

## Dates and `Temporal`

Prisma 8's `dateTime` codec takes a `Temporal.Instant` and rejects a plain
`Date`. The adapter converts at the boundary using `@js-temporal/polyfill`
(or `globalThis.Temporal` if your app already installed one), so neither
Better Auth nor your code ever sees a `Temporal` value.

## UUID ids

With `advanced.database.generateId: "uuid"` on PostgreSQL, the adapter
declares `supportsUUIDs: true`, like Better Auth's official Kysely, Drizzle
and Prisma adapters. Better Auth then leaves the id to the ORM:

- The contract uses Prisma 8's UUIDv7 preset: `@default(uuid(7))` in PSL,
  `field.id.uuidv7String()` in TypeScript. Both compile to the same thing.
- Ids are generated by the Prisma runtime before the insert, not by a
  database function, so there's no minimum PostgreSQL version.
- v7 ids are time-ordered, which keeps indexes efficient on insert-heavy
  tables.
- The id column is `character(36)`; foreign keys stay `text`, which
  PostgreSQL accepts for both constraints and lookups.

If you write your own contract with a different default
(`gen_random_uuid()`, for example), that default is used instead.
`supportsUUIDs` only tells Better Auth not to generate the id itself.

On SQLite, Better Auth keeps generating ids in application code.

## Case-insensitive matching

Case-insensitive filters use `ilike`, which the PostgreSQL adapter provides.
On any other provider they fall back to `like`. LIKE wildcards in user input
are escaped, including in each value of a case-insensitive `in` / `not_in`.
